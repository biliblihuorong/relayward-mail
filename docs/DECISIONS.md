# 开发决定记录（DECISIONS.md）

计划书未明确定义的行为，按「最简单、最安全」原则处理并记录于此。

## M1（2026-10-02）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-02 | 迁移文件 0001 是否只建 M1 用到的表 | `0001_init.sql` 一次性建立计划书数据模型的全部五张表和索引 | 计划书已给出完整 schema；已发布的迁移文件禁止修改，避免后续里程碑重复拆分建表迁移 |
| 2026-10-02 | M1 没有 管理 API（M2），无法创建发信程序，M1 无法独立验收 | 新增本机 CLI 子命令 `relayward admin create-app NAME [-from ADDR]`，打印一次性 SMTP 密码 | 「每个阶段结束都能独立使用」；本机命令不新增网络攻击面；不写审计日志（审计随 M2 API 一起实现） |
| 2026-10-02 | Dockerfile 要求 distroless（无 shell/curl）又要内置 HEALTHCHECK 调 /healthz | 新增子命令 `relayward healthcheck [-url URL]`，默认从 config 推导 admin 监听地址并 GET /healthz | 满足计划书对 distroless + HEALTHCHECK 的同时要求的最小做法 |
| 2026-10-02 | /healthz 在 M1 挂在哪个端口 | M1 先在 admin 监听（默认 :8081）上提供 /healthz，M2 在其上扩展管理 API；public 监听（:8080）M3 一起启动 | admin HTTP 服务是 /healthz 的宿主，避免 M1 空开 public 端口 |
| 2026-10-02 | 上游 5xx 永久拒绝时对程序返回什么 | 上游 4xx / 连接失败 → 451；上游 5xx → 554，日志记 `failed` | 计划书只定义了临时失败返回 451；永久失败若也返回 451 会导致程序无限重试 |
| 2026-10-02 | MAIL FROM 不在允许列表时返回什么状态码 | 550 5.7.1 `sender address not allowed` | 拒收语义明确；错误信息不含内部细节 |
| 2026-10-02 | 转发是否需要缓存整个消息 | DATA 阶段将消息读入内存（上限 `max_message_size`，默认 10MB），用于统计大小、提取 Subject / Message-ID 并转发 | M1 最简单做法；上限受 go-smtp 强制，不产生无限内存占用 |
| 2026-10-02 | SQLite 连接池大小 | 整个进程单连接（`SetMaxOpenConns(1)`），打开时设置 WAL / busy_timeout / foreign_keys | 单连接串行化写入，规避 SQLITE_BUSY；M1 规模下读并发不是瓶颈 |
| 2026-10-02 | SMTP 是否允许无 TLS 明文认证 | 配置了 `tls_cert` 时 AUTH 必须先 STARTTLS；未配置证书时允许明文 AUTH | 计划书允许内部网络不配证书；配了证书则默认收紧 |
| 2026-10-02 | SMTP 问候语 / EHLO 域名用什么 | 取 `public.base_url` 的 host，解析失败回退 `relayward` | 计划书配置里没有独立字段，用退订页域名最自然 |
| 2026-10-02 | 日志级别如何配置 | 环境变量 `LOG_LEVEL`（debug/info/warn/error，默认 info） | 计划书要求「级别可配置」但未指定载体，环境变量零配置成本 |
| 2026-10-02 | 日志保留天数清理（`log_retention_days`）落在哪个里程碑 | 随 M1 的发送日志一起实现（后台每日清理 `messages`） | 清理是日志功能的组成部分，M1 交付后即可长期独立运行 |
| 2026-10-02 | 上游转发客户端选 go-smtp 还是标准库 | 标准库 `net/smtp`（计划书两个选项之一） | go-smtp v0.25 客户端没有公开的单连接 STARTTLS 方法且 EHLO 名固定为 localhost；net/smtp 支持显式 STARTTLS、自定义 EHLO 名。注：`-race` 在 Windows 需要本机 C 编译器（gcc），本地已通过 scoop 安装，CI/Linux 原生可用 |
| 2026-10-02 | 配置加载对未知字段的处理 | 严格模式（`KnownFields(true)`），未知字段报错 | 拼写错误的配置键静默失效比启动失败更危险 |
| 2026-10-02 | `public.base_url` 的协议约束 | 只允许 `https`，否则启动报错 | 该地址会出现在发给收件人的退订链接中（M3），必须 HTTPS |

## M2（2026-10-02）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-02 | 删除程序后 messages 表 app_id 如何保持可追溯 | 迁移 0002 给 apps 加 `deleted_at` 软删除；同名字段重建时原地复活同一行（保留 id），日志 join 不丢名字 | 计划书要求「软删除或保留 id」；复活机制避免同名 409 死锁 |
| 2026-10-02 | 审计要求记录 token 名称，但 token 可能事后被吊销 | 迁移 0002 给 audit_log 加 `token_name` 列，写审计时固化名称 | 仅靠 token_id join 在吊销后丢失名称 |
| 2026-10-02 | 限流 0 值语义 | rate_per_hour 只接受正整数（0/负数 → 400），不提供「不限量」模式 | 防误配导致网关被打爆；计划书默认 500 |
| 2026-10-02 | 反向代理后的客户端 IP 来源 | 只取 TCP 对端地址，不信任 X-Forwarded-For | XFF 可伪造；代理场景所有请求共享代理 IP，运营需在代理层还原真实 IP |
| 2026-10-02 | 被锁定 IP 的 HTTP 响应 | 429 `{"error":{"code":"ip_banned"}}`，即使持有效 token 也拒绝 | 计划书状态码表有 429；与「统一 401」不冲突（401 针对凭据状态） |
| 2026-10-02 | /healthz 是否受失败锁定与 IP 白名单约束 | 不受；锁定与白名单只作用于 /api/* | 监控与 Docker HEALTHCHECK 的可用性不应依赖凭据，且 healthz 不泄露信息 |
| 2026-10-02 | CLI 写操作（create-app / admin reset）是否写审计 | 写；token_name 记为 "local-cli"/"system"，ip 记为 "local" | 计划书「所有写操作记录审计」；本地命令没有 Bearer token |
| 2026-10-02 | 统计接口的时间范围 | 全量统计，不提供时间窗参数 | 计划书未定义查询参数，选最简单做法；后续需要再加 since |
| 2026-10-02 | 创建的管理 token 前缀 | `rw_` + 43 字符 base64url；初始 token 按计划书保持 `rw_admin_` | 计划书只规定了初始 token 格式 |
| 2026-10-02 | /api 上不带 token 的请求是否计入失败锁定 | 计入（与无效 token 同样对待） | 缺 token 的探测同样是爆破行为 |

## M3（2026-10-02）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-02 | 计划书目录树把 `web/templates/` 放在仓库根，但 go:embed 不能引用包目录之外的文件 | 模板实际放在 `internal/web/templates/`，由 web 包直接 embed | go:embed 的硬性限制；目录位置不影响任何行为 |
| 2026-10-02 | 拆信后某个收件人上游失败，整体返回什么 | 与单发路径一致按上游错误性质映射：临时失败 451、永久失败 554；已成功收件人可能因程序重试收到重复邮件 | 静默丢失（返回 250）违背「上游临时失败由程序重试」的设计；去重队列属后续规划，第一版接受重复 |
| 2026-10-02 | 退订开关关闭的程序是否去 Bcc | 不去，完全原样转发（含 Bcc 头）；Bcc 剥离只发生在拆信路径 | 计划书「去掉 Bcc 头」列在拆信一节内，「退订开关关闭不拆、原样转发」是独立规则 |
| 2026-10-02 | 限流按消息还是按拆信后的副本计数 | 按消息（一次 DATA 一次令牌），不按收件人加倍 | 令牌桶语义是「程序每小时发信上限」，拆信是网关内部实现细节 |
| 2026-10-02 | POST /api/unsubscribes 重复添加同一 (app, email) | 幂等成功：新记录 201，已存在返回 200 和既有行（保留首次 source 与时间） | 退订天然幂等；409 会让重试脚本报错，没有收益 |
| 2026-10-02 | 收件人通过页面退订是否写审计日志 | 写：action `unsubscribe.create` / `unsubscribe.delete`，token_name 固定 `public`，记录 IP，token_id 为空 | 退订表本身记录 source，但审计还需要 IP 便于排查；管理页与 CLI 同样无 token 的场景已有先例（"local-cli"/"system"） |
| 2026-10-02 | 退订确认表单的 CSRF 方案 | GET 时种 `rw_csrf` Cookie（HttpOnly、SameSite=Lax、TLS 下 Secure），表单隐藏域与 Cookie 常数时间比对；RFC 8058 一键退订 POST（body 恰为 `List-Unsubscribe=One-Click`）豁免 CSRF；其余 POST 一律 400 | 邮件客户端无法参与 CSRF 握手，RFC 8058 场景下「持有 token 即授权」；表单场景标准双提交 Cookie 方案 |
| 2026-10-02 | 退订页的 CSP 允许什么 | `default-src 'self'; style-src 'unsafe-inline'; frame-ancestors 'none'`，页面不含任何脚本 | 页面用内联 `<style>`（邮件客户端场景无需外部资源）；放开 style-src 是最小让步 |
| 2026-10-02 | 程序被软删除后旧退订链接打开什么 | `GetAppByID` 不过滤软删除行；显示名依次取 display_name → name → 「该程序」 | 令牌无状态不含程序名，删除程序不应让历史退订链接 404 或报错 |
| 2026-10-02 | 程序自带 List-Unsubscribe 头时如何处理 | 网关仍注入自己的两个退订头，不与程序自带头去重 | 网关是退订的权威来源；程序自带头指向外部时以网关为准，重复头由收件端自行容忍 |
| 2026-10-02 | 退订页面文案是否可配置 | 第一版中文文案固定在模板内；邮件正文小字（`footer_text`）的可配置随 M4 实现 | 计划书允许页面中文；页面文案配置是低价值配置项，先不做 |
| 2026-10-02 | public 监听上的 /healthz 与 admin 端口的关系 | 同一处理逻辑（api.Server 导出 HealthzHandler），public 端点不需要 token | 计划书要求「三个端口都响应」健康检查；两端口语义一致便于监控配置 |

## M4（2026-10-02）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-02 | `footer_text` 未配置时的默认值 | 取计划书示例文案「不想再收到此类邮件？点此退订」 | 计划书配置示例给出了该文案，作为缺省最自然 |
| 2026-10-02 | `{app}` 占位符替换成什么 | display_name 非空用之，否则回退 SMTP 用户名 | 计划书说「取程序的 display_name」；未设置时不能渲染成空串 |
| 2026-10-02 | 正文注入解析失败时怎么办 | InjectFooter 任何结构性错误都返回原文，转发路径记 WARN 后按未注入正文发送（退订头照常注入） | 计划书风险表明确「解析失败时只注入头部、原样转发」；投递可用性优先于注入 |
| 2026-10-02 | multipart 的解析与重组方式 | 自实现边界分割器（复用原 boundary 重组），不用 mime/multipart 读取器 | 未注入的部件（附件等）必须字节级不变，multipart 读取器不保留原始头字节与折叠格式 |
| 2026-10-02 | 7bit / 无 Content-Transfer-Encoding 的文本部件如何处理 | 页脚必然引入非 ASCII 字节，升级为 quoted-printable 并改写 CTE 头 | 最简单且合规的重编码路径；base64/qp 保持原编码重编，8bit/binary 保持原样 |
| 2026-10-02 | 非 UTF-8 字符集（gbk 等）的文本部件 | 跳过不注入，其余部件照常 | 无法安全插入 UTF-8 页脚；宁缺勿乱码 |
| 2026-10-02 | 顶层消息没有 header/body 空行分隔 | 视为不可解析，原样转发并记日志 | 无法可靠重建该消息的框架结构 |
| 2026-10-02 | 存量程序的 body_injection 初值 | 迁移 0003 以 `DEFAULT 1` 落列，存量与新建程序默认开启 | 计划书将正文注入列为默认行为，`apps.unsubscribe` 同样默认开 |
| 2026-10-02 | text/plain 部件的页脚形式 | 仅追加空行 + `-- ` 分隔行 + 「退订：<链接>」，不渲染 footer_text 文案 | 计划书对 text/plain 的定义就是一行退订链接；文案（含 {app}）只出现在 HTML 小字中 |
| 2026-10-02 | 网关检测到 DKIM-Signature 的行为 | 跳过正文注入并记 WARN，退订头照常注入 | 计划书明确要求；改体会破坏客户端签名 |

## M5（2026-10-02）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-02 | 管理页挂在哪个端口和路径 | admin 端口（默认 :8081）的 `GET /admin`，JS/CSS 为同源静态文件 | 管理页属于管理面，与 /api 同端口便于「收紧时只关管理端口」；与 /healthz、/api 无路径冲突 |
| 2026-10-02 | 页面本身是否要求 token | 页面与静态资源不需要 token（静态壳，无数据），所有数据都来自带 Bearer 的现有 API 调用，401 时页面提示重新输入 | 计划书要求「输入 token 后可看」；静态壳不含任何数据，不新增攻击面 |
| 2026-10-02 | 页面脚本与样式能否内联 | 拆成独立的 app.js / style.css 内嵌文件，保持 api 面 CSP `default-src 'self'` 不放开 unsafe-inline | 内联脚本/样式需要放宽 CSP；拆文件零成本地保住严格 CSP |
| 2026-10-02 | token 在浏览器里怎么保存 | localStorage；页面无任何第三方资源与内联脚本，XSS 面由 CSP 收敛 | 纯运维自用单页；存 sessionStorage 会让每次开页都要重贴 token，得不偿失 |
| 2026-10-02 | 是否为页面新增后端接口 | 不新增，页面只调用既有 /api（计划书硬性要求） | 页面仅是 API 的 UI 壳 |

## 评审修复（2026-10-03）

| 日期 | 问题 | 决定 | 理由 |
| ---- | ---- | ---- | ---- |
| 2026-10-03 | `log_retention_days` 清理此前未接入 | serve 启动时清理一次，之后每 24 小时清理 `messages`；保留天数为 0 以下则不清理 | M1 决定已声明实现，但 `PruneMessages` 从未被调用 |
| 2026-10-03 | 拆信循环共用一个 10 秒 ctx，收件人多时查询退订表超时 | 每个收件人的退订查询单独设置超时 | 每个收件人一次上游往返，总耗时可超过单个超时，导致 451 后重试重复发送 |
| 2026-10-03 | 计划书要求 HTTP / SMTP 处理器外层 recover | SMTP 的 Auth/Mail/Rcpt/Data 返回 451；管理 API 返回 500 `internal_error`；退订页返回 500；均只记日志 | go-smtp 会话协程 panic 会使整个进程退出 |
| 2026-10-03 | PATCH 程序任意字段都会重置限流桶 | 仅请求带 `rate_per_hour` 时才重建桶 | 避免改其他配置时额度被刷新 |
| 2026-10-03 | 同一信封里重复的收件人 | 按规范化邮箱去重，接受但只投递一次 | 避免重复发信 |
